The Xbox controller drives the paddle motor **and** the rudder at the same time. RT = forward, LT = reverse, left stick = steer. You'll end with the boat on a stand (wheels off the ground), squeezing RT spinning the paddles, LT reversing, and the stick swinging the rudder — all live, at once.

<KeyTerms terms={[
  { term: "Command struct", definition: "\"Who decides\" vs \"what moves.\" A Command struct (throttle, steer, armed, stamp) sits between input and actuators. Inputs only fill a Command. Actuators only read one. They never touch each other directly. This is why a later session can swap in an autonomous input source without touching a single line of motor or servo code." },
  { term: "No mixing needed", definition: "A skid-steer robot has to combine throttle+steer into two different wheel speeds. This boat has one drive motor and a separate rudder servo, so throttle → the motor and steer → the servo, directly, no math to combine them." },
  { term: "Normalizing raw controller numbers", definition: "throttle() and brake() are 0…1023 each — divide by 1023, and combine as throttle = RT/1023 − LT/1023 for a signed −1…+1 value. axisX() is roughly −512…511 — divide by 512 for steer. Deadzone both using the threshold you found in E1." },
]} />

<Activity title="Your task" time="35 min" grouping="Electronics pair">

You're reusing your own `PaddleDrive` and `Steering` classes from E2/E3 — same interface, now driven by a controller instead of an automated sequence. We keep the **ramp** from E2 on throttle (so a slammed trigger doesn't yank the gear train) but send steering straight through — a servo is already mechanically limited and we want it responsive.

```cpp
#include <Arduino.h>
#include <Bluepad32.h>

constexpr int PIN_DRIVE_A = 27, PIN_DRIVE_B = 13, PIN_STEER = 25, PIN_LED = 33;
constexpr int MOT_FREQ = 5000, MOT_BITS = 10, MOT_MAX = (1 << MOT_BITS) - 1;
constexpr int SRV_FREQ = 50, SRV_BITS = 16, SRV_PERIOD_US = 20000;
constexpr int STEER_CENTER_US = 1500, STEER_RANGE_US = 400;   // your E3 trim values

constexpr float DEADZONE      = 0.06f;   // your E1 value
constexpr float THROTTLE_SLEW = 2.0f;    // max throttle change per second
constexpr float DUTY_CAP      = 0.40f;   // bench cap — raise with the real 12V motor

struct Command {
  float throttle = 0, steer = 0;
  bool  armed = false;
  unsigned long stamp = 0;
};

// --- paste your E2 PaddleDrive and E3 Steering classes here, unchanged ---

PaddleDrive drive;
Steering    steer;

ControllerPtr pad = nullptr;
void onConnect(ControllerPtr c)    { if (!pad) pad = c; }
void onDisconnect(ControllerPtr c) { if (pad == c) pad = nullptr; }

float deadzone(float v) { return fabs(v) < DEADZONE ? 0.f : v; }

bool readController(Command& cmd) {
  if (!pad || !pad->isConnected() || !pad->isGamepad()) return false;
  // TODO 1: fill cmd.throttle (RT/1023 - LT/1023, deadzoned) and
  // cmd.steer (axisX/512, deadzoned). Set cmd.armed = true and
  // cmd.stamp = millis(). Return true.
}

Command cmd;
float applied = 0.0f;
unsigned long lastLoop = 0;

void setup() {
  pinMode(PIN_LED, OUTPUT);
  drive.begin(); steer.begin();
  BP32.setup(&onConnect, &onDisconnect);
  BP32.forgetBluetoothKeys();
  BP32.enableVirtualDevice(false);
  lastLoop = millis();
  Console.println("\n[E4] RC integration. Boat on a stand — wheels off the ground!");
}

void loop() {
  unsigned long now = millis();
  float dt = (now - lastLoop) / 1000.0f; lastLoop = now;

  BP32.update();
  if (!readController(cmd)) cmd.armed = false;

  // TODO 2: compute `target` (cmd.throttle * DUTY_CAP if armed, else 0),
  // ramp `applied` toward `target` by at most THROTTLE_SLEW * dt per loop
  // (reuse the constrain-based approach idea from E2), then call
  // drive.set(applied) and steer.set(cmd.armed ? cmd.steer : 0.0f).

  digitalWrite(PIN_LED, cmd.armed ? HIGH : (now / 300 % 2));
  delay(10);
}
```

**Guiding questions:**
- Why does `readController` set `cmd.armed = true` unconditionally when the pad is connected, but `loop()` sets `cmd.armed = false` when it *isn't*? Where does "the controller went out of range" actually get handled by this design?
- What would visibly go wrong on the water if you forgot the deadzone on `cmd.steer`?

<Callout type="tip" title="Checkpoint — how to know it's working">
Boat/paddle assembly **on a stand, wheels off the ground**. Pair the pad — LED goes solid. Squeeze RT: paddles ramp up forward, smoothly (not a snap). Release: they ramp down. LT: reverse. Push the stick left/right: rudder swings **while the paddles keep spinning** — that simultaneity is the actual integration test. Turn the controller off: the LED starts blinking and the motor stops (a preview of E5's failsafe).

Four assignments and a `return true;` — nothing more. `cmd.throttle = deadzone(pad->throttle()/1023.0f - pad->brake()/1023.0f);` is the pattern; steer follows the same shape with `axisX()/512.0f`.
</Support>

<Support title="Hint 2 — TODO 2 shape">
This is the same ramp idea as E2's `approach()` helper, just inlined: `float target = cmd.armed ? cmd.throttle * DUTY_CAP : 0.0f;` then move `applied` toward `target` by at most `THROTTLE_SLEW * dt`, using `constrain(target - applied, -maxStep, maxStep)` added to `applied`.
</Support>

<Section title="Troubleshooting" icon="🩹" id="troubleshooting">

Phase-specific traps — general tooling issues are in the <SessionLink code="troubleshooting">Troubleshooting — Common Issues</SessionLink> page.

- **Pairs but nothing moves:** re-confirm E2 basics — switch ON, ≥6V on the jack.
- **Motor hums but won't turn (servo fine):** current starvation — the motor now shares the supply with the servo + Bluetooth radio. A 1A wall charger often isn't enough; a 2S 18650 pack is. If you switch supplies, also revisit `DUTY_CAP`.
- **Creeps at rest:** deadzone too small — raise `DEADZONE`.
