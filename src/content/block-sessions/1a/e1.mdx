Get your Xbox controller to connect to the ESP32 over Bluetooth and stream its stick/trigger values into the console. No motors, no servo — a pure software win. You'll end with the controller's Xbox light going solid, and a live readout changing as you move the sticks and squeeze the triggers.

<KeyTerms terms={[
  { term: "ESP32-WROOM-32E", definition: "Your board's chip pairs with any Xbox controller because it supports both Bluetooth radios (Classic and BLE) — smaller ESP32 variants (S3/C3/C6) only do BLE." },
  { term: "HID", definition: "The standard Bluetooth language a gamepad speaks. Bluepad32 is the library that understands it and hands you clean button/axis values." },
  { term: "espidf framework", definition: "Bluepad32 needs a different project skeleton than a plain Arduino sketch — it replaces the Bluetooth stack underneath Arduino, so the project is espidf-framework, not arduino, and your code lives in main/sketch.cpp." },
  { term: "Console, not Serial", definition: "Bluepad32 owns the USB serial console for its own use — printing with Serial gets you garbage or nothing. Use Console.printf(...) everywhere." },
]} />

<Section title="Git and GitHub — just enough to understand what you're about to do" icon="🔀" id="git">

You've done this once already with your teacher's help — this is the "why," briefly, not a git course. Three ideas, nothing more:

- **A repository ("repo")** is a project's files plus its entire history of changes, stored online on GitHub. Bluepad32's author keeps the exact project skeleton this course needs in one.
- **`git`** is the tool that tracks that history — every saved change is recorded, so nothing is ever silently lost and multiple people can work on the same project without overwriting each other.
- **`git clone <url>`** downloads a full copy of a repo — files *and* history — onto your computer, ready to build. The `--recursive` flag matters here specifically because this project is assembled from several smaller sub-projects bundled together (Bluepad32 is one) — recursive fetches those too, not just the outer shell.

That's the whole mental model you need for this course — clone once, build.

</Section>

3. **Before your first build**, apply the one-time patch for this machine — see <SessionLink code="troubleshooting">Troubleshooting — Common Issues</SessionLink> if you haven't already.

Moving the left stick should swing your printed value roughly from about −500 to +500 through zero; squeezing each trigger should climb from 0 toward ~1023. **At rest, your printed stick value should read exactly 0** — if it doesn't, your deadzone threshold is too small. Write down the deadzone threshold you land on; you'll reuse it in E4.

<Section title="Troubleshooting" icon="🩹" id="troubleshooting">

Phase-specific traps only — for anything else (install issues, upload failures, port not found) see the <SessionLink code="troubleshooting">Troubleshooting — Common Issues</SessionLink> page.

- **Garbage or nothing prints:** you used `Serial` somewhere instead of `Console`.
- **Controller never connects:** make sure no phone/PC is already paired to it — a controller only actively connects to one host. Turn Bluetooth off on nearby devices.
- **Connects, then drops immediately:** low controller battery, or too far away.
