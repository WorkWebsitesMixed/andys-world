The engineering notebook (cuaderno de ingeniería) is graded directly against the items below, straight from the challenge rubric. This page says **who** writes each item and **when**. The full fillable template is the <SessionLink code="notebook-template">Engineering Notebook Template</SessionLink> — use that as your working document; this page is the assignment map.

<Section title="Does it need to be a special notebook?" icon="❓" id="format">

No — there's no format requirement in the challenge rubric itself. The closest real-world equivalent, FIRST Robotics' engineering notebooks, explicitly allows either handwritten/bound **or** digital notebooks — the only thing that actually matters is that entries are **dated** and **can't be silently rewritten after the fact** (so a judge can trust the timeline is real, not backfilled the night before). Two options, either is fine:

- **A plain bound notebook** (any school composition notebook — nothing special to buy). Write in pen, date every entry, and **cross out mistakes rather than erasing them** — a crossed-out wrong idea is evidence of iteration, which is exactly what the rubric rewards.
- **A shared Google Doc or Sheet.** Zero new tools to learn, everyone can write at once, and its built-in version history already gives you the "can't be silently rewritten" property for free — open **File → Version history** to show a judge the real timeline if asked.

Pick whichever the team will actually keep up with — a notebook that's current beats a fancier one that's a week behind. This guide's structure (who writes what, when) works identically either way.

</Section>

<Callout type="info" title="The rule">
Some of this notebook is the whole team's, some is split by track. Don't silo more than the tables below say — the split is only for the technical deep-dive sections; everything else you build and revise together.
</Callout>

<Section title="Why it's split this way" icon="💭" id="why">

The rubric doesn't actually score "the design trio wrote 12 paragraphs" — it scores whether the *team* can explain design reasoning, testing rigor, iteration, teamwork, and communication. Splitting the deep-dive writing lets each section get written by whoever actually did that work and can speak to it — but the shared spine keeps everyone able to answer for the *whole* boat if a judge asks, which the technical sections alone won't give you.

</Section>
