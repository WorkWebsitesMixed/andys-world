The regular class teaches you to build a model and record what it reveals — genuinely valuable, and the core of C4 evidence. This session adds the question that decides whether a 30-minute model is well spent or wasted: what should you actually test first? Testing the easiest thing to test isn't the same as testing the thing most likely to reveal a real problem.

<Callout type="exam" title="Why this matters" id="why">
  <ExamLink to="project">Component 2 Criterion 4</ExamLink> rewards rigorous, evidenced development — and rigour starts with testing the right thing, not just testing *something*. A model that confirms what you already knew wastes the one chance a rough card build gives you to find a real problem cheaply.
</Callout>

<KeyTerms terms={[
  { term: "Risk-based test priority", definition: "Testing your biggest uncertainty first — the assumption most likely to be wrong, and most costly if it is — rather than the easiest or most obvious thing to test. A model's value is highest when it tests something you're genuinely unsure about, not something you're already confident works." },
  { term: "Rapid iteration", definition: "Cycling through build → test → change quickly and repeatedly within a single session, rather than perfecting one model slowly. Several rough, fast loops typically reveal more real problems than one careful, slow build." },
  { term: "Finite Element Analysis (FEA)", definition: "Computer software that simulates how a design distributes stress under load, without physically building it — the CAD model is divided into a mesh of small elements, and the software calculates stress in each one, usually displayed as a colour map (blue = low stress, red = high stress). A digital equivalent of a physical load test, used heavily in professional engineering before a physical prototype is ever built." },
]} />

<Section title="What to test first: risk, not convenience" icon="🎯" id="test-first">

Every design has several uncertainties — but they're not equally risky. Before building anything, ask: **which assumption, if wrong, would be the most expensive to discover late, and which one am I actually unsure about right now?** That's what the model should test first — not whatever happens to be easiest to build or check.

| Uncertainty type | Example | Test priority |
|---|---|---|
| High risk, genuinely unsure | Will the base tip under an asymmetric load? | Test first — expensive to discover after manufacture |
| Low risk, already confident | Does the LED light when the switch closes? | Test later, or trust the Term 1 breadboard result |
| High risk, but not testable with a card model | Will the laser-cut joint really hold at full scale? | Note as a risk to test in Week 5/6, not this session |

A student who spends the model session confirming the switch position (already tested in Term 1) instead of testing whether the untested base geometry is stable has tested the wrong thing — technically "did a test," but not the test that reduces the most risk.

</Section>

<Section title="Rapid iteration: several rough loops beat one careful build" icon="🔁" id="iteration">

Given a fixed 45 minutes, a single, carefully-built model tested once produces one data point. The same time spent on two or three rough, fast build-test-change loops produces several — and each loop after the first is informed by what the previous one revealed, which a single careful build never gets the chance to be.

**The habit:** build the roughest version that can answer the question you're testing (not a polished one), test it immediately, change one thing based on what you found, and re-test — repeating as many times as the session allows. Documenting each loop (what happened, why it matters, what changed) is what turns rapid iteration into C4 evidence rather than just fiddling.

</Section>

<WorkedExample title="Risk-prioritised, rapidly iterated model session">

**Uncertainty audit (2 minutes):** the student lists three uncertainties — base stability under asymmetric load (untested, high risk), switch reachability (already checked informally, lower risk), overall proportions looking right (checked visually against the sketch, lowest risk). Base stability is the clear priority.

**Loop 1 (12 min):** rough card frame, base footprint 150 mm. Loaded asymmetrically with one weight on one side — tips at a load well below the 4 kg spec. Development point recorded: tips, base too narrow.

**Loop 2 (10 min):** same model, base widened to 210 mm with a scrap-card extension taped on. Re-tested with the same asymmetric load — holds. Development point recorded: widening the base to ~210 mm resolves the tipping, confirmed by re-test.

**Loop 3 (8 min):** with the highest-risk uncertainty now resolved, remaining time tests the second-priority item (switch reachability) rather than re-confirming what loop 2 already settled.

**Result:** three loops, two genuine problems investigated in priority order, each with a recorded before/after — far stronger C4 evidence than one slow, careful model that only tested proportions.

</WorkedExample>

<Extension title="Taste beyond: prototyping fidelity, and testing without building at all">

Industry distinguishes **low-fidelity prototyping** (card, foam — fast, cheap, tests form and basic function, disposable) from **high-fidelity prototyping** (close to final materials and finish — slow, expensive, tests details a rough model can't). The rule of thumb: test the biggest uncertainties with the cheapest, fastest model that can answer the question, and save high-fidelity builds for questions only a near-final version can resolve. **Finite Element Analysis (FEA)** goes a step further: professional engineers often test a structure's stress distribution entirely inside CAD software, before any physical model exists at all, using a colour-coded stress map to spot a weak point that a physical model would only reveal by breaking. It's the same "test cheaply before committing" logic as a card model, just without needing to build anything physical first.

</Extension>

<Activity title="Risk audit, rapid iteration, TA-prep" time="45 min" grouping="Individual, HOD circulating" materials={["Card, foam board, masking tape", "Your chosen design sketch and specification", "Scissors, craft knife, cutting mat"]}>

**0–10 min — Preview.** Recap why model, model types, and testing form/scale/stability from the regular class.

**10–25 min — Test-driven development.** List your three biggest design uncertainties and rank them by risk (likelihood of being wrong × cost of discovering it late). Build the roughest model that can test your #1 priority.

**25–35 min — Prototyping taste.** Read the extension box. Note which of your project's uncertainties, if any, could theoretically be tested with FEA instead of a physical model.

**35–45 min — TA cue rehearsal + Challenge.** Read the TA prep box, then complete the challenge: run at least one full build-test-change loop, documenting what happened, why it matters, and what you changed as a development point.
</Activity>

<Support title="TA prep: model flaws as data, not failure">

**Common error to watch for:** a peer feels discouraged when their model breaks or tips, and treats it as a failed attempt rather than useful information.

**Your tutoring cue:** *"What did making it reveal that drawing it didn't?"* — this reframes the flaw as the model doing its job, not the student doing something wrong.

</Support>
